# 第1章：搭建项目架构

## 本章定位

- **数据流定位**：管线起点 —— 建立五个包的边界与工程骨架 → 后续所有章节都在这套包结构上工作。
- **难度**：★★☆☆☆ —— 全册的地图章。只要求建立「react / react-reconciler / renderer」三层心智模型，不涉及具体算法。
- **前置依赖**：无（本系列起点）。只要求写过 React 应用、熟悉组件与 Hooks 等常用 API 的用法。自检：知道 JSX 不是浏览器原生语法、需要编译；能用组件 + Hooks 写过一个可交互页面。
- **读后检验**：能说出五个包各负责「声明 → 计算 → 执行」的哪一段；能说出提交代码时会触发哪些自动检查。

这一章的重点不是记住工具配置项，而是两件事：看懂目录结构与五个核心包的分工、知道本章已经建立了哪些工程约束。包边界理解清楚后，后面学习 Fiber、Hooks 和 Scheduler 时，才知道每段代码为什么属于当前位置。

## 整体架构思路：声明、计算与执行分包

### 目录结构

本章完成时，仓库里还没有一行 React 源码，只有根目录的工程配置文件：

```text
big-react/
  .husky/pre-commit       提交钩子
  .prettierrc.json        格式配置
  babel.config.js         Babel 配置
  eslint.config.mjs       ESLint 配置（flat config）
  package.json            根包（公共依赖与脚本）
  pnpm-workspace.yaml     workspace 声明
  tsconfig.json           TypeScript 配置
```

`packages/`、`demos/`、`scripts/`、`docs/` 这些目录是后续章节逐步长出来的——这正是本课程的路线图：

| 目录        | 职责                                 | 出现时点                                             |
| ----------- | ------------------------------------ | ---------------------------------------------------- |
| `packages/` | 五个源码包（职责划分见下方包职责表） | 第 2 章创建 react 包                                 |
| `demos/`    | Vite 调试页面，按主题分目录          | 第 2 章开始用于包解析调试                            |
| `scripts/`  | 构建与测试脚本（Rollup、Jest 配置）  | Rollup 配置随第 2 章打包加入，Jest 配置在第 9 章搭建 |
| `docs/`     | 讲义与相关文档                       | 讲义即本课程的配套文档                               |

几个值得注意的点：

- `packages/` 里每个包都有自己的 `package.json`，逻辑上是独立 npm 包，由 pnpm workspace 在本地关联（见「为什么使用 monorepo」）。
- `demos/test-fc/` 下的入口用于后续章节调试包解析；本章只需理解文档中的 JSX 片段，不依赖某个入口文件。
- `scripts/rollup/` 放各包的构建配置，`scripts/jest/` 放测试环境与初始化脚本；它们的配置细节属于后续章节的工程基础，本章不展开。

#### 五个核心包分工

`packages/` 下是 big-react 将要实现的五个核心包。五个包沿「声明 → 计算 → 执行」的方向各管一段：

| 包                    | 职责段         | 一句话职责                               | 详讲章节      |
| --------------------- | -------------- | ---------------------------------------- | ------------- |
| `react`               | 声明           | 提供 JSX、Hooks 等公共 API，不执行组件   | 本章、第 2 章 |
| `shared`              | 跨包协议       | 各包共用的 Symbol 与类型                 | 本章          |
| `react-reconciler`    | 计算           | Fiber、调度、diff，生成变化标记          | 第 3 章起     |
| `react-dom`           | 执行（浏览器） | 渲染入口与浏览器宿主操作                 | 第 6 章       |
| `react-noop-renderer` | 执行（测试）   | 渲染成普通对象，用于断言 reconciler 行为 | 第 16 章      |

这五个包会在后面的章节创建。

### 为什么使用 monorepo？

这些包边界清晰，但一次 React 功能通常需要跨包修改。例如实现 ref 可能同时涉及：

- react：从 JSX 中提取 ref
- react-reconciler：把 ref 保存到 Fiber 并标记副作用
- react-dom：在 commit 阶段绑定 DOM 实例
- 测试 renderer：验证绑定和解绑顺序

如果每个包位于独立仓库，一个功能需要协调多个版本、多个 PR 和本地联调。monorepo 让跨包修改可以在一次提交中完成，同时仍通过 package 目录维护职责边界。

所以 monorepo 解决的是协作与一致演进，不等于“所有代码可以互相随意引用”。恰恰相反，物理上放在一个仓库，更需要逻辑包边界约束依赖方向——big-react 靠各包 package.json 的依赖声明与 hostConfig 的构建注入实现（后者第 6 章展开）。

big-react 使用 pnpm workspace，本章的 `pnpm-workspace.yaml` 配置：

```yaml
packages:
	- 'packages/*'
```

此时只声明了源码包目录。后续调试页面不作为 workspace 成员，而是通过 Vite alias 直接解析源码包。workspace 让源码包之间可以引用本地实现，不必先发布 npm 版本。根目录主要管理 TypeScript、Rollup、Jest、ESLint 等共同工具。

## 本章实现：建立工程反馈环

### 本章工程状态总账

| 输入                  | 写入位置                                                 | 消费者                        | 可观察结果                                  |
| --------------------- | -------------------------------------------------------- | ----------------------------- | ------------------------------------------- |
| 未来源码包的目录规则  | `pnpm-workspace.yaml`                                    | pnpm workspace                | pnpm 会把随后创建的 `packages/*` 识别为成员 |
| TypeScript 与代码规范 | `tsconfig.json`、`eslint.config.mjs`、`.prettierrc.json` | 编辑器、tsc、ESLint、Prettier | 类型、代码质量和格式采用统一规则            |
| 暂存区中的代码文件    | `lint-staged` 配置与 `.husky/pre-commit`                 | Git 提交钩子                  | 提交前检查并格式化本次暂存的代码文件        |

这张表只跟踪工程信息写到哪里、由谁读取。工具配置本身不是 React 原理，但如果依赖方向或公开入口错误，后续源码即使逻辑正确也无法按预期运行。

### 工程配置：先建立静态反馈环

> **本节数据流**：源码与配置 → TypeScript、ESLint、Prettier 消费 → 输出类型、代码质量与格式反馈。

本章的根 `package.json` 已安装后续课程所需的依赖，但目前仓库只有工程配置，没有源码包、构建配置、测试配置或 demo。此时真正建立起来的是三条静态反馈：

| 工具       | 本章已有输入        | 产生的反馈                     |
| ---------- | ------------------- | ------------------------------ |
| TypeScript | `tsconfig.json`     | 为随后创建的源码包统一类型规则 |
| ESLint     | `eslint.config.mjs` | 报告代码质量问题               |
| Prettier   | `.prettierrc.json`  | 统一代码格式                   |

构建、测试和浏览器调试会在对应章节接通；仅仅安装依赖并不等于这些反馈环已经能够工作。

根 package.json 此时已经预写 `build:dev`、`demo` 和 `test` 脚本，但它们指向的 Rollup、Vite、Jest 配置与源码目录尚不存在。脚本名只表达后续工程意图，当前可执行反馈只有配置读取与提交钩子，不能把三条脚本列入本章已经闭环的能力。

### 开发规范：提交时自动触发的检查

> **本节数据流**：Git 暂存文件 → Husky 触发 lint-staged 与 typecheck → ESLint/Prettier/tsc 消费 → 只有满足约束的改动进入提交。

在提交环节自动执行代码质量检查。本章的一次 `git commit` 依次经过：

```text
git commit
  -> husky 触发 pre-commit 钩子（.husky/pre-commit）
  -> lint-staged：只对本次暂存的代码文件执行
       eslint --fix --quiet（自动修复并隐藏警告，错误仍会阻断提交）
       prettier --write（统一格式）
```

本章的 pre-commit 脚本还保留一行 `echo "hello"`，随后执行 `npx lint-staged`。它没有执行全量 TypeScript 检查，因此不能把“提交成功”理解为全仓类型已经通过。

各工具的配置位置与分工：

#### ESLint：静态检查

配置在根目录 `eslint.config.mjs`（flat config），启用 `typescript-eslint` 与 `eslint-plugin-react`，主要规则：

- `@typescript-eslint/no-unused-vars`、`no-explicit-any`、`ban-ts-comment`、`no-constant-condition`：未使用变量、滥用 any 等提示为警告。

这些 TypeScript 相关规则大多设为 warn；而 ESLint 推荐规则中的 error 仍可阻止 lint-staged 成功。TypeScript 类型错误是否阻断提交则取决于是否另行执行 `tsc`，本章钩子没有做这一步。

#### Prettier：统一格式

配置在根目录 `.prettierrc.json`：Tab 缩进、单引号、行宽 80、不保留尾逗号。格式问题一律交给 Prettier 自动重写，ESLint 只管代码质量，两者不重复检查同一件事。

#### Husky + lint-staged：把检查挂到提交动作

`pnpm install` 时 `prepare` 脚本自动安装 husky 钩子，无需手动配置。lint-staged 的配置在根目录 `package.json` 里，只对暂存区里的代码文件运行——检查量小、反馈快，不会把整个仓库的历史问题算在你头上。

#### 提交信息规范：不约束

本课程不引入 commitlint：没有配置文件、也没有 `commit-msg` 钩子，提交信息格式不受约束。若后续想约束提交信息，需要补上 commitlint 配置与钩子两步。

开发规范不是给学习增加仪式感。本章先把“暂存文件 → lint/格式化”接到提交动作；类型、构建、测试与浏览器反馈会随着后续代码逐步接通。

## 与官方 React 的差异

- 官方仓库有远超 5 个包：`react-native-renderer`、`react-server`、`react-art`、`react-test-renderer` 等；big-react 只保留理解主线所需的 5 个。
- 官方把 `react-reconciler` 作为独立 npm 包发布，第三方 renderer（如 React Native 的自研层）可以按 renderer 协议接入自己的宿主操作实现；big-react 的 reconciler 只在本仓库内被 react-dom / react-noop-renderer 消费。

这些差距不影响第一章的结论：**每个包的边界都对应「声明 → 计算 → 执行」中一段明确的职责，而不是按功能名称随意分目录。**

## 思考题

### Q1: 为什么选择 Monorepo 而不是 MultiRepo?

big-react 的一次功能往往跨越声明层、reconciler 和 renderer。如果使用 MultiRepo，同一次协议修改要分别发布或链接多个仓库，版本稍有错位就可能出现“调用方已升级、实现方未升级”的问题，调试也难以复现完整链路。Monorepo 让跨包改动、共享类型和统一检查处于同一个工作区，适合这种需要同步演进的源码项目。

但 Monorepo 只解决协作与版本一致性，不会自动保证架构边界。每个包仍应声明自己的依赖，不能因为物理上在同一仓库就任意跨层引用；否则五包设计只剩目录形式，没有隔离价值。

### Q2: Monorepo 实现方案有哪些？pnpm workspace 相比 npm/yarn workspace 有什么优势？

基础方案包括 npm、Yarn、pnpm 自带的 workspace；Nx、Turborepo、Rush、Lerna 等工具会在 workspace 之上增加任务编排、缓存、发布或依赖图能力。选型先看问题规模：本课程只需要本地包发现和依赖安装，pnpm workspace 已经足够，不需要先引入复杂编排层。

pnpm 的关键优势不只是“快”：内容寻址 store 减少重复文件；依赖默认隔离得更严格，包如果没有声明依赖，通常不能偶然从根目录拿到它，从而更早暴露幽灵依赖；`workspace:` 协议还能明确表达“这里必须消费仓库内版本”。代价是部分依赖扁平结构的旧工具可能需要额外配置，所以它不是无条件优于所有方案，而是很适合强调包边界的 big-react。

### Q3: ESLint 和 Prettier 的职责边界是什么？如何避免两者冲突？

ESLint 判断代码是否可能有语义或维护问题，例如未使用变量、危险控制流和不合规 API；Prettier 只决定同一段代码如何排版，例如缩进、引号与换行。二者的输出应能分别回答“代码有没有问题”和“代码长什么样”，否则一次格式差异会被两个工具重复报告。

`eslint-config-prettier` 的职责是关闭会与 Prettier 冲突的 ESLint 格式规则，但本章只是把它安装进依赖，`eslint.config.mjs` 并没有引入它。因此当前真正避免冲突的手段只有：ESLint 配置没有主动增加格式规则，lint-staged 最后再由 Prettier 统一排版。这是一个配置缺口，不能把“依赖已安装”写成“冲突规则已关闭”。若要补齐，应把该配置显式接入 ESLint flat config；这不改变 ESLint 管质量、Prettier 管排版的职责边界。

## 本章小结

第一章建立的是整套源码的工程骨架与地图：react 位于声明层，reconciler 位于计算层，renderer 位于执行层。先建立「声明 → 计算 → 执行」的全貌与五个包的分工，后面各章逐个包落地实现时，才不会把 React 源码看成一串互相调用的文件。

不过，仓库现在只有工程配置：lint、格式化、workspace 都就位了，却连一个 `packages/` 目录都还没有——没有任何代码能被浏览器执行。让 JSX 先变成对象，是第 2 章。

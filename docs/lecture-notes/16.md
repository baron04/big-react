# 第16章：实现 noop-renderer

## 本章定位

- **数据流定位**：测试调用 noop root → reconciler 产生宿主操作 → noop hostConfig 写入普通对象树 → root API、对象引用和 yield 日志提供断言结果。
- **难度**：★★★☆☆ —— 算法并不复杂，重点是设计一个足够真实、同时可控可观察的测试宿主，并让它完整经过 reconciler 的正常流程。
- **前置依赖**：第 6 章（ReactDOM hostConfig 与 commit）、第 9 章（Jest 与公开包测试）、第 15 章（passive effect）。自检：能区分 render 计算出的 flags 与 commit 调用的宿主操作。
- **读后检验**：能解释 noop renderer 如何支持 reconciler 单元测试；能区分对象身份、最终 JSX 与 yield 日志各自能证明什么；能指出 hostConfig 的移动和删除操作必须维护哪些不变量。

前十五章主要通过 DOM 观察结果，测试容易同时卷入 reconciler、ReactDOM hostConfig 和浏览器环境。本章实现 `react-noop-renderer`，目的不是渲染真实界面，而是为 reconciler 提供一个不依赖浏览器、行为可控且结果可直接断言的单元测试宿主。

noop renderer 把 HostComponent 和 HostText 渲染成普通 JavaScript 对象，测试可以直接检查树结构、对象身份和 effect 时序。实现这一测试工具仍要复用正常的 reconciler 与 hostConfig 协议，因此也会顺带暴露核心层对 DOM 的越界依赖，但检验解耦是实现过程带来的架构收益，不是它的首要目的。

## 整体架构思路：为 reconciler 提供可控的测试宿主

reconciler 负责回答：

```text
创建哪个 Host 实例
插入到哪个父节点
放在谁前面
删除哪个旧节点
更新哪个已有实例
```

renderer 负责把这些意图变成具体宿主操作：

```text
                    ┌→ ReactDOM hostConfig → DOM 节点
react-reconciler ───┤
                    └→ Noop hostConfig     → 普通对象树
```

两种 renderer 共享 Fiber、beginWork、completeWork、Diff、flags 和 commit 遍历。它们只在 HostInstance 的形态以及创建、插入、删除、更新的实现上不同。

### 单元测试为什么仍要经过正常 reconciler

如果 reconciler 中出现：

```ts
document.createElement(type);
node.parentNode.removeChild(node);
```

noop renderer 就无法接入。正确依赖方向应是：

```text
reconciler 依赖 hostConfig 协议
renderer 提供 hostConfig 实现
构建阶段为不同 renderer 注入对应实现
```

如果测试绕过 reconciler，直接把 ReactElement 转成对象树，只能验证转换函数本身，无法覆盖 Fiber 创建与复用、Diff、flags、commit 和 effect。noop renderer 必须像 ReactDOM 一样接收 reconciler 的宿主操作，只把最终落点换成普通对象。

这要求 reconciler 只依赖稳定的 hostConfig 协议；若核心代码直接调用 DOM API，noop renderer 就无法工作。因此，依赖边界正确是测试 renderer 成立的前提，也是接入它时可以检验出的架构性质。

### noop 仍要实现真实的树语义

不用 DOM 不等于可以随意修改数组。reconciler 会把 Placement 同时用于“插入新节点”和“移动已有节点”，所以 noop hostConfig 必须模拟宿主树真正需要的不变量：

- 一个 child 同一时刻只能处于一个位置。
- append 已存在的 child 表示移动到末尾，不能复制引用。
- insertBefore 已存在的 child 表示移动到目标位置，删除旧位置后要修正索引。
- remove 后 parent 与 children 两侧关系必须一致。
- update 应修改原实例，保持宿主身份。

若这些语义不成立，最终 JSX 可能偶然正确，对象身份和后续移动却已经错误，测试反而会给 reconciler 错误的安全感。

### 三种观察面回答不同问题

| 观察面                   | 最适合证明                               |
| ------------------------ | ---------------------------------------- |
| HostInstance 对象引用/id | 节点是复用还是重建                       |
| `getChildrenAsJSX`       | 最终宿主结构、文本与顺序                 |
| Scheduler yield 日志     | render、effect destroy/create 的执行顺序 |

只断言最终 JSX，无法发现“结果相同但实例被错误替换”；只比较对象 id，又不能证明 children 顺序正确。测试需要根据目标选择观察面。

## 本章实现：从 HostConfig 到可断言输出

### 本章改动文件

- hostConfig.ts：定义 noop Container、Instance、TextInstance 与宿主操作。
- root.ts：创建 reconciler root，并提供 `render/getChildren/getChildrenAsJSX`。
- index.ts：导出 noop renderer 公共入口。
- react-noop-render.config.js：生成 `react-noop-renderer` 构建产物。
- completeWork.ts：通过构建注入的 hostConfig 创建、更新宿主实例。
- commitWork.ts：把 renderer 相关更新下沉到 hostConfig。
- ReactEffectOrdering-test.js：验证 passive unmount 顺序。
- reactTestMatchers.js：用 `getChildrenAsJSX` 实现 `toMatchRenderedOutput`。

### noop 宿主对象模型

[hostConfig.ts](../../packages/react-noop-renderer/src/hostConfig.ts) 定义三种对象：

```ts
interface Container {
	rootID: number;
	children: Array<Instance | TextInstance>;
}

interface Instance {
	id: number;
	type: string;
	children: Array<Instance | TextInstance>;
	parent: number;
	props: Props;
}

interface TextInstance {
	text: string;
	id: number;
	parent: number;
}
```

它们分别对应 root 容器、HostComponent 与 HostText：

| Fiber         | noop 结果      | DOM renderer 中的对应物 |
| ------------- | -------------- | ----------------------- |
| HostRoot      | `Container`    | root DOM container      |
| HostComponent | `Instance`     | HTMLElement             |
| HostText      | `TextInstance` | Text                    |

`id` 用于观察对象身份，`parent` 和 `children` 共同描述宿主树，`props` 保存宿主节点收到的属性。Fragment、FunctionComponent 等非宿主 Fiber 不创建 Instance。

### 16-1 实现 noop renderer

#### 创建 HostComponent 与 HostText

`completeWork` 不直接构造对象，而是调用注入的 hostConfig：

```text
HostComponent → createInstance(type, props)
HostText      → createTextInstance(content)
```

首次挂载时，`appendAllChildren` 会穿透没有宿主实例的 Fiber，把顶层 Host 后代加入新建 Instance.children。这个过程与 ReactDOM 相同，只是目标从 DOM 节点换成普通对象。

#### 提交 Placement

commit 阶段已经计算出宿主父节点和 `before`：

```text
before 存在
→ insertChildToContainer(child, parent, before)

before 不存在
→ appendChildToContainer(parent, child)
```

reconciler 不关心 `parent.children` 是浏览器维护的节点列表还是 JavaScript 数组，只依赖 hostConfig 满足相同语义。

当前 noop 实现首次插入可以形成对象树，但移动已有节点仍有缺口：

- `appendChildToContainer` 直接 `push`，已有 child 会出现重复引用。
- `insertChildToContainer` 先记录 `beforeIndex` 再删除旧 child；若旧位置在 before 前面，删除后目标索引应减一，当前代码没有修正。

这说明“调用了正确的 hostConfig 函数”只是 reconciler 一侧的正确性，renderer 仍要兑现移动协议。

#### 更新职责从 react-dom 下沉到 hostConfig

接入第二个 renderer 时，`completeWork` 不能继续直接调用 ReactDOM 的 `updateFiberProps`。本章把通用层改为只标记 Update：

```text
completeWork
→ 比较新旧 props
→ 标记 Update

commitWork
→ 调用当前 renderer 的 commitUpdate
```

ReactDOM 可以在自己的 `commitUpdate` 中更新 DOM 属性和事件 props 缓存；noop 可以更新普通对象。核心层只负责决定“需要更新”，不负责知道“如何更新”。

本章 noop 的 `commitUpdate` 只处理 HostText，普通 HostComponent props 还没有实现原位更新。这是 renderer 能力缺口，不应重新把具体处理塞回 reconciler。

#### 删除宿主节点

删除由 reconciler 找到需要移除的顶层 Host 后代，再调用：

```ts
removeChild(container, child);
```

当前 noop 会从 `container.children` 删除 child，但没有把 `child.parent` 恢复为未挂载状态。最终输出中节点已经消失，不过对象两侧关系并不完全一致；若后续复用该对象，错误 parent 会影响挂载检查。

### 16-2 打包 noop renderer

noop renderer 需要像 `react-dom` 一样获得自己的 hostConfig。Rollup 配置把 reconciler 中的 hostConfig 引用替换到：

```text
react-dom 构建
→ packages/react-dom/src/hostConfig.ts

react-noop-renderer 构建
→ packages/react-noop-renderer/src/hostConfig.ts
```

这不是复制两套 reconciler，而是给同一核心算法注入两个宿主实现。

[root.ts](../../packages/react-noop-renderer/src/root.ts) 通过公共 reconciler 入口创建 root：

```ts
const container: Container = {
	rootID: idCounter++,
	children: []
};
const root = createContainer(container);
```

`render` 仍经过 `updateContainer`，所以 noop 测试覆盖的是正常 Fiber 更新流程，不是绕过 reconciler 手工创建对象。root 向外提供四项能力：

```ts
return {
	_Scheduler: Scheduler,
	render(element) {
		return updateContainer(element, root);
	},
	getChildren() {
		return getChildren(container);
	},
	getChildrenAsJSX() {
		return getChildrenAsJSX(container);
	}
};
```

### 16-3 把对象树转换成断言结果

`getChildrenAsJSX` 递归读取 Container/Instance/TextInstance：

```text
空 children      → null
单个 child       → child 对应 JSX
多个文本 child   → 拼接为字符串
多个结构 child   → 数组或 Fragment 形态
Instance         → { $$typeof, type, key, ref, props }
```

这样 matcher 可以写成：

```jsx
expect(root).toMatchRenderedOutput(
	<div>
		<span>hello</span>
	</div>
);
```

断言关注用户可观察的宿主输出，不需要暴露 Fiber 私有字段。需要验证复用时，再配合 `getChildren` 比较对象引用或 id。

### 用 Scheduler 日志验证 effect 卸载顺序

[ReactEffectOrdering-test.js](../../packages/react-reconciler/src/__tests__/ReactEffectOrdering-test.js) 在 Parent 与 Child 的 passive cleanup 中写入 Scheduler 日志：

```jsx
function Parent() {
	useEffect(() => {
		return () => Scheduler.unstable_yieldValue('Unmount parent');
	});
	return <Child />;
}
```

删除整棵子树后期望：

```js
expect(Scheduler).toHaveYielded(['Unmount parent', 'Unmount child']);
```

这个测试同时穿过：

```text
noop root.render(null)
→ reconciliation 标记删除
→ commitDeletion 遍历子树
→ 收集 passive unmount
→ flushPassiveEffects
→ Scheduler matcher 读取顺序
```

最终 JSX 只能证明节点消失，yield 日志才能证明 cleanup 的先后顺序。

### 本章实现边界

本章已经接通第二个 renderer 的创建、首次挂载、HostText 更新、对象输出和 effect 顺序测试，但 noop hostConfig 还没有完整模拟宿主树：

| 能力                       | 本章状态                   | 影响                        |
| -------------------------- | -------------------------- | --------------------------- |
| 首次 append                | 已实现                     | 可以构造初始对象树          |
| 已有 child 移动到末尾      | append 会复制引用          | keyed move 结果不可信       |
| insertBefore 移动          | 删除旧位置后未修正索引     | 某些重排会偏一位            |
| remove                     | 删除 children，不清 parent | 对象两侧关系不一致          |
| HostText update            | 已实现                     | 文本可原位更新              |
| HostComponent props update | 未实现                     | 普通 props 更新无法完整断言 |

这些边界集中说明了一个原则：普通对象并不会自动成为可靠的测试宿主。只有每个 hostConfig 操作都满足宿主不变量，noop renderer 的断言才足以反映 reconciler 的真实行为。

## 与官方 React 的差异

| 能力         | big-react 本章                        | 官方 React                               |
| ------------ | ------------------------------------- | ---------------------------------------- |
| 定位         | 最小课程测试 renderer                 | 用于 React 内部算法与调度测试            |
| HostInstance | 简单对象与数组                        | 更完整的对象宿主模型                     |
| 移动/删除    | 仍有索引、重复引用和 parent 缺口      | 维护与 reconciler 约定一致的宿主语义     |
| 更新         | 主要覆盖 HostText                     | 覆盖更多实例与提交行为                   |
| 观察工具     | 输出 JSX、对象引用、Scheduler matcher | 具有更完整的调度日志、错误与并发测试设施 |

核心设计是一致的：用一个不依赖 DOM 的 renderer 观察 reconciler。差异在于 big-react 的宿主协议覆盖范围和测试基础设施都更小。

## 思考题

### Q1: 为什么 jsdom 不能完全替代 noop renderer？

jsdom 仍然实现 DOM 节点、属性、事件和父子约束。测试失败时，问题可能来自 reconciler、react-dom hostConfig 或 jsdom 行为。noop renderer 把宿主结构缩小为普通对象，使实例身份、children 顺序和宿主操作都可以直接观察。

两者不是替代关系：noop 适合验证宿主无关算法，jsdom 或真实浏览器适合验证 ReactDOM 集成结果。

### Q2: noop renderer 为什么必须经过正常 reconciler，而不能直接把 ReactElement 转成对象树？

单元测试的目标是验证 reconciler。若直接转换 ReactElement，Fiber 创建与复用、Diff、flags、commit、Hook 和 effect 都被绕过；即使对象树正确，也不能说明这些流程正确。

noop renderer 因此只替换宿主实现：它与 ReactDOM 共享同一套 reconciler，通过 hostConfig 接收创建、插入、删除和更新意图，再把结果写入普通对象。这个结构既让内部行为可观察，也要求 reconciler 不直接依赖 `document`、`HTMLElement` 或 `parentNode`。后者是测试工具成立的架构前提与附带检验，不是另一个独立目标。

### Q3: noop 的 append 为什么不能简单执行 `children.push(child)`？

Placement 既表示插入新节点，也表示移动已有节点。DOM 的 `appendChild(existingNode)` 会先从旧位置移除，再把节点放到末尾，不会留下两份引用。若 noop 只执行 push，移动会变成复制，最终对象树不再满足一个 child 只有一个位置的不变量。

### Q4: insertBefore 移动已有 child 时，为什么删除顺序会影响索引？

假设 children 为 `[A, B, C]`，要把 A 插到 C 前。删除前 C 的索引是 2；先删除 A 后数组变为 `[B, C]`，C 的索引变成 1。若仍按旧索引 2 插入，会得到 `[B, C, A]`。

因此应在删除后重新查找 before，或在旧 child 位于 before 之前时修正目标索引。

### Q5: 为什么 `getChildrenAsJSX` 不能证明 HostInstance 被复用？

两次 render 即使都输出 `<div>hello</div>`，也可能一次复用原对象、另一次删除后重建。序列化结果相同，只能证明最终结构一致。

要验证复用，应通过 `getChildren` 保存前后对象引用或 id，再与 JSX 输出组合断言：对象相同证明身份复用，输出变化证明实例被正确更新。

### Q6: 为什么 effect 顺序要用 Scheduler 日志，而不是只检查最终输出？

cleanup 不一定改变宿主树。Parent 和 Child 的 destroy 即使顺序相反，最终 JSX 都是空，结构断言无法发现问题。Scheduler 日志记录执行过程，使测试可以验证 parent/child cleanup 的时间顺序。

### Q7: noop renderer 已经能够首次挂载，是否足以证明 hostConfig 抽象正确？

只能证明创建路径和依赖方向基本接通。更新、移动和删除会调用不同宿主操作，并依赖更严格的父子关系与实例复用语义。首次挂载成功不能推出 insert、remove、commitUpdate 都正确。

完整验证至少需要覆盖创建、原位更新、同层重排、移动、删除和 effect 卸载，并分别检查输出结构与对象身份。

## 本章小结

本章通过 noop renderer 为 reconciler 建立了可控的单元测试宿主：核心层生成宿主意图，构建阶段注入 noop hostConfig，普通对象树再通过 root API 和 matcher 变成可观察结果。

要让这些测试可信，既要求核心代码只依赖宿主协议，也要求 noop hostConfig 真正维护移动、删除和更新不变量。本章已经建立对象身份、最终输出和 effect 顺序三类观察面，但 noop 的部分树操作仍需补齐。下一章先用独立调度 Demo 理解时间切片，第 18 章再把并发调度接入 reconciler。

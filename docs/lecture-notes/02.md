# 第2章：JSX 转换

## 本章定位

- **数据流定位**：消费 JSX 语法（编译时）→ 产出 ReactElement → 被第 3 章创建 Fiber、第 9 章测试断言消费。
- **难度**：★★☆☆☆ —— 只涉及 `react` 包的声明层，数据结构简单，重点是理解「编译时 / 运行时」的分工与 `ReactElement` 的字段设计。
- **前置依赖**：第 1 章（包边界，知道 `react` 只负责声明、不执行组件）。自检：能说出 `<div>` 编译后大致变成什么函数调用。
- **读后检验**：能画出「JSX 语法 → 函数调用 → ReactElement」的完整数据流；能对着源码指出 `key/ref` 为什么留在 element 上而不进 props。

本章进入 `react` 包。JSX 本身不是浏览器能执行的语法，它需要先被 Babel 转换成函数调用，再由 React 运行时把这些函数调用转换成 `ReactElement`。本章实现的是“运行时”这一半。

## 整体架构思路：ReactElement 只是声明快照

先只看一段最普通的输入：

```jsx
<div id="root">hello</div>
```

阅读本章前先预测三个结果：Babel 会把它变成什么调用？runtime 返回对象的 type 与 props 是什么？此时是否已经存在 Fiber 或 DOM？整章都围绕这三个问题展开。

JSX 的核心价值不是“让 JavaScript 可以写 HTML”，而是提供一种声明式 UI 语言。React 必须回答：**如何把这种语法变成一个与浏览器、组件执行和更新算法都解耦的中间表示？**

一个看似更简单的方案，是让 JSX 编译后直接创建 DOM：

```js
const div = document.createElement('div');
div.textContent = 'hello';
```

这样会让编译结果过早决定执行方式：函数组件还没有机会执行，同一份 JSX 无法渲染到 Native/noop，React 也拿不到“前后两次 UI 描述”做协调。因此 JSX 编译不能产生最终宿主实例，只应产生普通函数调用；运行时再把调用规范化成 `ReactElement`。

这个中间表示需要满足以下约束：

1. 能表达宿主节点、函数组件、Fragment 等不同类型。
2. 能携带 props 和 children，但不能包含 DOM 专属行为。
3. 能携带影响节点身份的 `key` 和实例通道 `ref`。
4. automatic runtime 与经典 runtime 虽然参数形状不同，输出协议必须一致。
5. 它只描述一次渲染意图，不保存跨更新的状态和调度信息。

所以 `ReactElement` 的定位是不可执行的声明快照：

```mermaid
flowchart LR
    A["JSX 源码"] -->|"Babel（编译时）"| B["JSX runtime 函数调用"]
    B -->|"React runtime（运行时）"| C["ReactElement"]
    C --> D["Reconciler：创建或复用 Fiber"]
    D --> E["Renderer：根据提交结果创建宿主实例"]
```

JSX runtime 只负责把语法输入归一化成稳定的 ReactElement；它不创建 DOM，也不决定组件怎样执行。后续 reconciler 能否统一处理不同 JSX 写法，取决于这里输出的对象协议是否一致。

### 三种对象不要混淆

| 对象         | 生命周期                      | 主要回答的问题                     |
| ------------ | ----------------------------- | ---------------------------------- |
| ReactElement | 每次 JSX 求值产生             | 用户这一次想要什么？               |
| Fiber        | 跨 render 被 current/WIP 复用 | 这个节点过去是什么、现在要做什么？ |
| DOM/宿主实例 | commit 后真实存在             | 页面最终如何呈现？                 |

如果把 ReactElement 当作 Fiber，就没有地方稳定保存 state、alternate、Lane 和 flags；如果让 ReactElement 直接持有 DOM，就会破坏 renderer 无关性。这正是 React 需要三层表示而不是一个“万能虚拟 DOM 对象”的原因。

### `key` 与 `ref` 为什么不是普通 props？

`key` 参与 reconciler 的身份判断，`ref` 由 commit 阶段控制实例绑定；组件业务通常不应把它们当普通输入透传。把二者从 `props` 提取出来，是在数据结构层面声明其所有权：

```text
props -> 交给组件或宿主节点使用
key   -> 交给 reconciler 决定复用身份
ref   -> 交给 commit 阶段管理实例生命周期
```

这不是 API 上的偶然限制，而是三个阶段职责不同的结果。

## 本章实现：从 JSX 语法到打包产物

### ReactElement 生成账本

| 时刻         | 输入                         | 写入对象/字段                              | 下一步消费者          | 结果                                |
| ------------ | ---------------------------- | ------------------------------------------ | --------------------- | ----------------------------------- |
| 编译时       | JSX 语法                     | `jsx/jsxDEV` 调用参数                      | React runtime         | JSX 被消除，但尚未创建 Fiber 或 DOM |
| runtime 入口 | `type`、`config`、`maybeKey` | 局部变量 `key/ref/props`                   | ReactElement 构造逻辑 | 控制字段与业务 props 被拆开         |
| runtime 返回 | 归一化后的字段               | `ReactElement.$$typeof/type/key/ref/props` | 后续 reconciler       | 得到一次 render 的声明快照          |
| 构建         | 源码入口与包名               | `dist/node_modules/react` 的运行时入口     | demo                  | JSX 产物可在浏览器工程中被加载      |

后面的每个实现分节都应能落回这张表：先确认拿到哪种调用参数，再看写入 ReactElement 的哪个字段，最后确认下游只依赖稳定协议而不依赖入口差异。

JSX 经过转换、补全和打包，最终成为可加载的模块。

### 2-1 实现 JSX

> **本节数据流**：Babel 生成的 runtime 调用参数 → `jsx` 读取并归一化 `key/ref/props` → 写入 ReactElement → reconciler 获得统一输入。

本步建立「语法到对象」的转换：先定义 ReactElement 数据结构，再实现 `jsx` 方法。2-2 随后把这些入口接入打包配置。

#### JSX 转换是什么？

现代 JSX 默认使用 automatic runtime。下面的代码：

```jsx
<div id="root">hello</div>
```

会被 Babel 转换为：

```js
import { jsx as _jsx } from 'react/jsx-runtime';

_jsx('div', {
	id: 'root',
	children: 'hello'
});
```

经典 runtime 则会转换为：

```js
React.createElement('div', { id: 'root' }, 'hello');
```

所以 JSX 转换分两段：

- 编译时：Babel 负责把 JSX 语法变成函数调用。
- 运行时：React 负责实现这些函数，返回 `ReactElement`。

big-react 只实现运行时。本章可正确支撑 automatic runtime 的 `jsx/jsxDEV` 调用和 classic runtime 的 `createElement` 调用。

#### ReactElement 数据结构

`ReactElement` 是 JSX 被消费前的静态描述。它不是 Fiber，也不是 DOM 节点。它只回答一个问题：用户这次写了什么 UI？

核心字段如下：

```ts
const element = {
	$$typeof: REACT_ELEMENT_TYPE,
	type,
	key,
	ref,
	props,
	__mark: 'KaSong'
};
```

这段代码来自 `ReactElement` 工厂函数（`packages/react/src/jsx.ts`）。`$$typeof` 取的是 [REACT_ELEMENT_TYPE](../../packages/shared/ReactSymbols.ts)，在有 `Symbol.for` 的环境里是 `Symbol.for('react.element')`，否则退回数字 `0xac7`。

字段含义：

- `$$typeof`：标记这是一个 ReactElement，避免把普通对象误当成元素。
- `type`：元素类型。本章只是原样保存它；字符串与函数分别为后续宿主组件、函数组件留下输入。
- `key`：同级 diff 时使用的稳定身份。
- `ref`：后续 commit 阶段绑定实例。
- `props`：组件或 DOM 节点的参数，`children` 也放在这里。

`ReactElement` 的设计刻意很轻。它不保存父子指针、不保存状态、不保存副作用，因为这些属于 Fiber 的职责。

#### 实现 jsx 方法

> **设计要点**：key 需要字符串化（`'' + maybeKey`），因为 diff 时按字符串做等值比较；ref 最终形态应保持原始对象引用（函数或 `{ current }` 对象），由 commit 阶段调用或赋值。key 与 ref 都应从 config 中单独提取、不进入 props——它们是元素的保留字段，而不是组件的数据。

[jsx(type, config, maybeKey)](../../packages/react/src/jsx.ts) 的目标是三件事：

1. 从 `maybeKey` 或 `config.key` 中提取 `key`。
2. 从 `config.ref` 中提取 `ref`。
3. 把剩余字段复制到 `props`。

设计上需要注意：`key` 和 `ref` 是 ReactElement 的保留字段，不应该继续留在 `props` 中。否则组件里会误以为自己能通过 `props.key` 读取 key。

本章进度下的实际实现还是起步形态：

```ts
export const jsx = (type: Type, config: Props, maybeKey?: Key) => {
	let key: Key | null = null;
	const props: Props = {};
	let ref: Ref = null;

	if (maybeKey !== undefined) {
		key = '' + maybeKey;
	}

	for (const prop in config) {
		const val = config[prop];

		if (prop === 'key') {
			if (val !== undefined) {
				key = '' + val;
			}
			continue;
		}

		if (prop === 'ref') {
			if (val !== undefined) {
				ref = val;
			}
			continue;
		}

		if (Object.prototype.hasOwnProperty.call(config, prop)) {
			props[prop] = val;
		}
	}

	return ReactElement(type, key, ref, props);
};
```

### 2-2 实现 JSX 的打包

> **本节数据流**：runtime 源码入口 → Rollup 写出包主入口、`jsx-runtime` 与 `jsx-dev-runtime` → demo 按公开路径加载。

本步为 react 包配置 Rollup 打包，产出包主入口与两份 JSX runtime 文件——第 1 章的包边界从此有了可被 demo 直接消费的产物。

#### 本章实际导出的运行时入口

JSX 编译产物分属两种 runtime。

1. **classic runtime**：最早的形态。编译器把 JSX 转成 `React.createElement(type, config, ...children)` 调用，要求当前作用域里有 `React` 变量——这就是旧代码每个文件都要写 `import React from 'react'` 的原因。children 通过剩余参数传递，key 混在 config 里。
2. **automatic runtime**：React 17 引入，是现在的默认形态。编译器自动注入对 `react/jsx-runtime` 的 import，用户代码不再需要导入 React；参数形状为`(type, config, maybeKey)`，children 放进 config，key 单独作为第三参传递。

本章实际只有一个对象构造实现，经过源码导出和构建形成三个名字：

| 入口            | 来源                      | 本章能力                                               |
| --------------- | ------------------------- | ------------------------------------------------------ |
| `jsx`           | `src/jsx.ts`              | 读取 `(type, config, maybeKey)` 并创建 ReactElement    |
| `jsxDEV`        | `src/jsx.ts`              | 直接别名到 `jsx`，没有开发期校验                       |
| `createElement` | `packages/react/index.ts` | 读取 `(type, config, ...children)` 并创建 ReactElement |

automatic runtime 的多子节点入口 `jsxs` 要到第 6 章才补为 `jsx` 的别名；本章构建产物尚未导出它。

### 2-4 从 ReactElement 字段回看声明层边界

前三节已经分别完成 runtime 字段写入、公开入口构建和消费验证。现在只用这些实际产物回答设计问题：为什么入口可以不同而对象必须相同，为什么 key/ref 的所有权不能落进 props。

理解 JSX 最有效的方式是追踪一份数据跨越的边界：

```text
<Button key="save" disabled>保存</Button>
        编译期↓
jsx(Button, { disabled: true, children: '保存' }, 'save')
        运行期↓
ReactElement {
  $$typeof, type: Button, key: 'save', ref: null,
  props: { disabled: true, children: '保存' }
}
```

第一步由编译器完成，React 没有解析尖括号；第二步才由本章的 `jsx` 完成。所以“JSX 就是 ReactElement”并不准确：JSX 是语法，编译结果是函数调用，调用结果才是 ReactElement。

#### 为什么 ReactElement 不能同时充当 Fiber？

ReactElement 是本次 UI 的轻量描述，适合频繁重建。Fiber 则跨更新保存 `stateNode`、`return/child/sibling`、`alternate`、状态和副作用。如果合并两者：

- 本次 render 创建的新描述会覆盖上次工作状态；
- 调度和副作用字段会泄漏进公共对象；
- 同一个逻辑节点无法拥有 current/WIP 两份工作记录。

因此第 2 章只生产声明层对象，第 3 章才把它消费成计算层对象。

#### `key`、`ref` 与 `props` 为什么分开？

`key` 是 reconciler 匹配同级 children 身份的内部信息，`ref` 是 commit 阶段绑定实例的信息，它们都不是组件的普通业务输入。运行时应把它们从输入中提取出来，不放入 props：automatic runtime 的编译器把 key 放到第三参 `maybeKey`，ref 则从 config 提取。

```jsx
function Item(props) {
	console.log(props.key); // undefined
}

<Item key={123} />; // element.key 会被规范化
```

key 只要求在同一组 siblings 中稳定且唯一，不要求全局唯一。children 则留在 props，因为对 FunctionComponent 来说，它本来就是一种普通输入。

#### 本章已经稳定的输入协议

本章已经稳定的是 `jsx/jsxDEV` 的输出协议：无论开发入口还是普通入口，最终都是同一种 ReactElement。编译器认 `react/jsx-runtime` 的导出，后续 reconciler 只认 ReactElement 字段，不需要知道对象来自哪个构建文件。`createElement` 与 `jsxs` 的完整调用兼容性尚未闭环，不能把“对象工厂相同”扩写成“所有 runtime 入口已完全一致”。

## 与官方 React 的差异

- 官方 React 的 dev 版 `jsxWithValidation`/`jsxDEV` 会为 element 附加 `_source`、`_self`、`_owner` 等调试字段，并在 props 合法性、`key` 使用上给开发期警告；big-react 只做运行时转换，省略这些调试信息。

这些差距不影响协议主线：**编译结果 + 运行时 = 带 `$$typeof` 标记的 ReactElement。**

## 思考题

### Q1: JSX 是编译时能力还是运行时能力？

JSX 语法的消除发生在编译时，但编译结果仍要在运行时调用 JSX runtime，所以完整链路同时包含编译时和运行时能力。编译器负责把 `<div id="app">hello</div>` 转成函数调用，本章的 `jsx` 执行调用并创建带 `$$typeof/type/key/ref/props` 的 ReactElement。此时组件没有执行，也没有 Fiber 或 DOM。排错时应按边界定位：转换结果错误查编译配置，对象字段错误查 runtime；对象如何继续变成可执行工作，则从第 3 章开始。

### Q2: 为什么 JSX 不直接编译成 `document.createElement`？

直接生成 DOM 命令会在编译阶段写死宿主环境，也会失去新旧描述可比较的中间层。React 需要先得到 ReactElement，才能在 render 阶段决定复用、删除或移动哪些 Fiber，并把真正的宿主操作延迟到 commit。这样同一组件既可以交给 DOM renderer，也可以交给 noop、服务端或其他 renderer。代价是多了一层描述对象，但换来了跨宿主、可调度和可中断的架构空间。

### Q3: key 与 ref 为什么不在 props 中？

因为它们分别属于 reconciler 和 commit 的控制协议，而不是组件的普通输入。`key` 在父节点的同级 children 中决定跨 render 的身份匹配，第 12 章会用它参与列表 Diff；`ref` 记录实例绑定意图，第 20 章在 commit 阶段消费。若把它们混进 props，组件可能把控制字段当业务数据，下游也必须反复从 props 中剥离。组件确实需要相同值时，应另传 `itemKey` 等普通属性。

## 本章小结

JSX 运行时把用户写的 UI 转成 `ReactElement`。`ReactElement` 是后续 reconciler 的输入，但它本身不参与调度、状态和副作用。理解这一层边界，后面看到 Fiber 时就能明白：Fiber 不是 JSX 的另一种写法，而是 React 为了执行更新流程引入的工作单元。

不过，`ReactElement` 现在只是个普通对象：没有任何代码消费它，它既不会变成 DOM，也不知道如何更新。给它配一套「工作单元 + 双缓存」的执行架构，从第 3 章的 Fiber 开始。
